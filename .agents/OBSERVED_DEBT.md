# Observed debt

Concrete out-of-scope debt, gaps, risks or defects noticed while working. Each entry: evidence, impact, suggested next move. Update entries in place.

## OD-1 — `e2e_recovery` kill-window legs are timing-flaky (pre-existing, backend-independent)

* **Evidence (2026-10-08):** on the committed SQLite baseline (`git worktree` at `691ec1c`, isolated target dir) `cargo test -p gauntlet-cli --test e2e_recovery` failed in 4 of 14 sequential runs (2/8, 2/6). Failing tests were always the same two: `the_kill_in_the_produce_window_resumes_with_the_production_recovered` (assertions at `e2e_recovery.rs` ~729/747: dispatch count / production-row count off by one) and `the_kill_after_the_production_record_pins_the_resume_exactly_once_claim` (~1001). On the PostgreSQL cut-over the same two tests fail in the same way at a similar-or-higher rate (5/8 in one sample, small n). A post-kill writer-quiescence barrier (`test_support::quiesce_writers`, keyed on `application_name`) was added and is correct for PostgreSQL, but did not change the rate — the cause is not a late server commit.
* **Mechanism (observed):** the test polls for one durable production row and then SIGKILLs the child. Under load the child can complete another produce→re-attempt cycle between the poll and the kill (pre-kill logs show the same `evidence_ref` produced twice, ~5 s apart), so the "kill landed here" branch the assertions assume is sometimes not the branch that happened.
* **Impact:** recovery proofs P7/T-kill legs cannot be treated as deterministic evidence; AGENTS.md §4 ("repeated green races prove only the branch that happened to win"). Not caused by, and not worsened in kind by, the PostgreSQL migration.
* **Next move:** replace poll-then-kill with a deterministic pause at the boundary — a test-only hook in the mock runner/controller that blocks at the produce boundary until the test has taken its durable snapshot and sent SIGKILL — and add one deterministic variant per branch (row already present / absent / settled).
* **Re-measured (2026-10-09, end of the fabric series):** at `758b2c1` (before the OD-5/6/9/10 commits, separate worktree and target dir) `e2e_recovery` failed 4 of 6 sequential runs with the same two tests; at the series head `614949b` it failed 4 of 9 isolated runs and failed once in the full workspace run (2220 passed, 2 failed — exactly these two). Failure seen: `e2e_recovery.rs:1016` dispatch count 3, expected 2. The rate is unchanged by this series, so it is not a regression, but it is a standing source of non-deterministic gate results.

## OD-2 — workbench `PrimeDelegationDispatcher` is a test-matrix-only projection with diverging policy

* **Evidence (2026-10-08 recon):** no production TS caller of `PrimeDelegationDispatcher.delegate` (only `testing/cross-surface-matrix.ts:712`, optional ref in `prime-long-running.ts:365`); production model-facing `rlm.spawn` is emitted by Rust (`gauntlet-adapter-agent-prime/src/program.rs`). TS policy is `max_depth=3, max_children_per_parent=4`; the Rust prime adapter defaults `max_depth=1` (`config.rs` DEFAULT_MAX_DEPTH). `childCount` (prime-recursion.ts ~384) counts ALL sessions with that parent, not concurrently admitted ones as the policy doc says.
* **Impact:** two unreconciled depth/child policies; T09–T11 proofs exercise a dispatcher production does not call. The Agent Fabric's Rust `DelegationBroker` + `InvocationGraph` is now the canonical implementation of these semantics.
* **Next move:** after Phase F's fabric host exists, route the workbench projection through it and delete/limit the TS dispatcher to a client; align the limits in one config source; count only non-terminal children.

## OD-7 — `cli_surface` doctor smoke writes `crates/gauntlet-cli/.agents/reports/doctor.json`

* **Status: resolved in working tree.**
* **Evidence:** running `cargo test -p gauntlet-cli` leaves an untracked `crates/gauntlet-cli/.agents/` directory; the arch literal scan then fails (258/261) until it is removed.
* **Root cause (found 2026-10-09):** production defect, not a test defect. `doctor::assemble` skipped the environment layer when no `GAUNTLET.md` was discovered (`(None, None)` arm used `EffectiveConfig::from_defaults()` without calling `resolve`), so `GAUNTLET_REPORT_DIR` was ignored and the report fell back to `<project root>/.agents/reports`. The tests that set the variable (`fabric_cli`, `fabric_acceptance` doctor runs) therefore still wrote into the crate directory, which is the cwd under `cargo test`.
* **Fix:** the no-contract arm now runs `resolve` with no front matter, so the environment layer applies (`crates/gauntlet-app/src/doctor/mod.rs`). Regression test: `the_report_dir_env_is_honoured_without_a_contract`.

## OD-9 — codemode adapter: parallel bound, memory class and caller-side cancel

* **Status: resolved (c56e532 memory class, 614949b cancel).**
* **Memory:** `ProgramLimit::Memory` (wire `memory`, catalog token `heap` because `memory` is a reserved adapter segment in core crates); real-engine test `guest_heap_exhaustion_is_a_memory_limit`.
* **Parallel bound:** enforced by the trusted Bun host against the guest's unsettled-call count; the Rust side cannot enforce it (the parent answers one call at a time). Accepted.
* **Cancel:** `ProgramHost::cancelled()` / `CancelProbe` carry the owner's cancellation into the runtime. The adapter polls in `CANCEL_POLL_SPAN` slices and before servicing every call; on cancellation it admits no further call, sends `cancel`, waits the bounded ack, stops the host, and returns `ProgramStatus::Cancelled` (distinct from timed_out, failed, limit_exceeded). `DriverHost` refuses calls once cancelled (`call_cancelled`, trace Refused) without reaching the invoker. The fabric host probes the caller's graph node and treats a terminal status as cancellation (a lookup error is not cancellation and is logged once). Cancellation writes no settlement. Proof: contract case `cancellation_stops_further_calls` (reference runtime and the real adapter), real-engine test `a_cancelled_owner_stops_the_program_before_its_timeout` (stable over repeated and single-threaded runs; the Bun process is gone afterwards), acceptance test `acceptance_cancelling_the_caller_stops_its_running_program` (a `while (true) {}` program ends `cancelled` in under half the timeout; the node differs only in status/terminal_at; no settlements or SettlementCommitted events).
* **Remaining:** cancellation is observed through the graph. If the harness process dies without the node ever becoming terminal, a running program still ends only at its own deadline (then the serve loop sees EOF). The graph poll is one node lookup per slice.

## OD-10 — native `rlm.spawn` children inherit their Prime parent's MCP caller identity

* **Status: resolved by invocation-bound control-plane attribution (ee85ebb, live proof 69f7b6d).** The caller stays the AUTHORITY principal; it no longer establishes which execution is making a control-plane request. The Prime bridge provisions tagged env references for `RLM_DEPTH` and `RLM_SESSION_DIR` on the MCP server entry and starts `fabric serve` with `--session-binding RLM_DEPTH=0`. `fabric serve` evaluates the binding once at startup; an unbound host still answers `initialize`/`tools/list` but refuses EVERY `tools/call` (`agents.*` and `program.run`) with `unbound_execution` before any service, graph or budget access. A native child's server process observes `RLM_DEPTH=1` and its own `RLM_SESSION_DIR`, so it can never act as the invocation. No connection-order race: the binding depends on the process environment, not on who connected first.
* **Why this mechanism:** the MCP process receives nothing from Prime unless the settings ask for it (observed: with no `env` refs the server saw no session variables at all). With refs, the root session's server saw `RLM_DEPTH=0` and the native child's saw `RLM_DEPTH=1` plus a distinct `.../sub-<id>` session dir (observed with a real model, 2026-10-09).
* **Proof:** acceptance tests with a real `fabric serve` over stdio and PostgreSQL: a bound process works; mismatched or missing env refuses spawn/cancel/status/collect/program.run and leaves the graph (nodes, status, parent, depth, budget slices) unchanged; the parent's child-limit still applies afterwards and an unbound cancel leaves the child running while a bound cancel takes it. Live (ignored) test `live_prime_native_child_cannot_act_as_its_parent`: real Prime parent spawned one child through `agents.spawn`, a native `rlm.spawn` child tried the same with another key and got `unbound_execution`; graph = root + one child, no node for the native child's key.
* **Correction to an earlier entry:** the first live run (2026-10-09) recorded the model as `clinepass/cline-pass/deepseek-v4-flash`. It actually ran on `openai-codex/gpt-5.5` (Prime ignored the flags: the scratch settings lacked the extension package that provides `clinepass`, and a shared daemon held state). Later runs used `clinepass/cline-pass/kimi-k3`, verified from the session records.
* **Remaining (documented, not blocking):** a native child is NOT registered as a Gauntlet invocation, so it has no control-plane access at all (fail closed) rather than its own node. Registering native sessions as first-class invocations would need Prime to report them; nothing in Prime 0.9.8 exposes that to the MCP boundary beyond the env reference. The bridge does not carry `packages`/`npmCommand`, so a bridged profile cannot use extension-provided providers (such as `clinepass`) unless the profile's settings add them; the live test patches them in.

## OD-11 — bridged credentials: does a token refresh reach the canonical `auth.json`?

* **Status: resolved by evidence (2026-10-09, Prime 0.9.8). Prime owns the OAuth lifecycle; Gauntlet consumes authenticated Prime execution and does not persist provider credentials.**
* **Earlier hypothesis (disproved for this Prime):** that Prime's atomic replace would swap the per-invocation `auth.json` symlink for a regular file and strand the refreshed token. Observed instead: with the invocation agent dir's `auth.json` a file symlink to `~/.prime/agent/auth.json`, a real refresh left the symlink intact and updated the canonical store.
* **Experiment (`clinepass` OAuth, real model `cline-pass/kimi-k3`, scratch agent dir with `auth.json`/`models.json` symlinked to the canonical dir; metadata only, never values):** (1) valid credential, 48 min to expiry; (2) canonical expiry forced 60 min into the past; (3) a normal Prime run (`reply ok`) made the model call, which refreshed: canonical access-token fingerprint changed, expiry became +49.9 min, the agent dir's `auth.json` was STILL a symlink and showed the same refreshed token with no copying; (4) expiry forced again, then a run whose parent spawned a native `rlm.spawn` child: the child answered, canonical refreshed again (+49.5 min), symlink intact; (5) a fresh Prime process afterwards (restart) worked with the access token unchanged (no needless refresh); (6) the invocation agent dir (logs, sessions, transcripts) contained no access or refresh token material; Gauntlet's adapter only checks `is_file` and creates the symlink, and never reads credential contents (`no_secret_is_copied_and_credentials_are_linked_not_copied`).
* **Limits of the evidence:** `clinepass` did not rotate its refresh token during the test (fingerprint unchanged), so rotation semantics were not exercised; `openai-codex` (the other stored OAuth login) was rate limited by its provider at the time and was not exercised. The symlink-write-through behavior is Prime 0.9.8's; a Prime change to replace the file would be caught by re-running the experiment. The test touched the user's real canonical store (forced expiry, then a legitimate refresh); the credential ended valid. The single transient `Upstream stream ended` turn in the sessions was a network event, not an auth failure.
* **Not built:** no sync, copy-back or token handling in Gauntlet.

## OD-12 — the Prime launch inherits the full parent environment; there is no env allowlist

* **Evidence:** `ProcessKernelTransport::submit` and the control calls use `std::process::Command` with no `env_clear()`, so a Prime parent inherits every variable the Gauntlet process has, including provider keys. The phase plan describes an env allowlist that the adapter does not implement. Slice 1b adds only `PRIME_AGENT_CODING_AGENT_DIR` (`rpc_command` in `transport.rs`) and leaves inheritance unchanged.
* **Impact:** not a regression, but the "env stays an allowlist" premise is false today. Credentials reach the harness through inheritance, not through the bridge.
* **Next move:** decide whether the Prime launch should `env_clear()` and pass an explicit allowlist (HOME, PATH, TMPDIR, the provider keys the chosen profile needs). That is a behavior change and needs approval.
