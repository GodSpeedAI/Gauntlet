# Prime-Agent Mission: Bootstrap a Reference-Anchored Gauntlet Runtime

## Mission

Starting from the current folder, design, implement, prove, and progressively dogfood a **portable Gauntlet runtime** for agentic work.

The finished system must let an operator provide a desired transformation plus a concrete comparison representation, then autonomously orchestrate:

**Reference → Transform → Observe → Compare → Verify → Select → Correct → Settle → Remember**

The system must be portable across agent harnesses, model providers, MCP servers, CLIs, repositories, operating systems, and implementation languages.

Do not build a Claude-specific, Codex-specific, Prime-Agent-specific, or model-specific workflow.

Prime-Agent is the initial **orchestrator adapter**, not the architecture.

The architecture must survive replacement of Prime-Agent.

---

# 1. Governing Idea

A Gauntlet is not:

* an agent;
* a prompt;
* a critic;
* a model;
* a skill;
* a set of MCP tools;
* a graph shape;
* a test suite.

A Gauntlet is a **governed comparison-and-correction protocol**.

An actor attempts a transformation.

Independent observation converts the resulting consequence into an inspectable representation.

A context-isolated comparator compares that observed representation against a declared reference representation.

Verifiers evaluate hard claims against evidence.

The controller materializes the residual difference and selects the next affordable corrective transformation.

The process continues until the work settles, reaches a stopping gate, exhausts its allowed payment, or requires escalation.

Canonical loop:

```text
REFERENCE
   ↓
TRANSFORM
   ↓
REALITY / ARTIFACT
   ↓
OBSERVE
   ↓
OBSERVED REPRESENTATION
   ↓
COMPARE ← REFERENCE
   ↓
RESIDUALS
   ↓
VERIFY
   ↓
SELECT NEXT AFFORDABLE CORRECTION
   ↓
CORRECT
   ↓
repeat

until:

SETTLED
BLOCKED
BUDGET_EXHAUSTED
ESCALATED
ABORTED
```

# 2. Non-Negotiable Invariants

Preserve these throughout implementation.

## 2.1 Reference and implementation are separate

The builder must never be allowed to silently modify the standard against which its work is evaluated.

At the beginning of every run:

1. resolve the active reference;
2. normalize it;
3. compute its digest;
4. freeze that version for the run.

The run may propose a future reference revision.

It may not change the active reference and then claim success against the changed standard.

---

## 2.2 Observation is not the builder's completion claim

Never evaluate solely from:

```text
builder says it is complete
builder summary
builder reasoning
builder-generated description of runtime behavior
```

Observe the resulting system independently wherever possible.

Examples:

```text
git state
files
compiler results
tests
runtime behavior
browser state
screenshots
API responses
logs
metrics
benchmarks
static analysis
security scans
formal checks
external sources
human evaluation
```

Produce an explicit Observation Bundle.

---

## 2.3 Critic is not verifier

Keep these roles distinct.

**Critic / Comparator**

Determines:

```text
How does observed reality differ from the intended reference?
```

It may identify qualitative, architectural, semantic, experiential, or cross-cutting deficiencies.

**Verifier**

Determines:

```text
Do specific claims satisfy declared evidence requirements?
```

Prefer deterministic verification when the property is deterministically measurable.

Do not ask an LLM to judge something a compiler, test, schema validator, policy checker, benchmark, browser probe, or other deterministic instrument can establish more reliably.

---

## 2.4 Builder cannot review itself

A builder may run local checks while working.

That does not constitute independent comparison.

Every formal comparison pass must use a fresh isolated context.

The comparator must not receive:

* the builder's conversational history;
* the builder's chain of reasoning;
* rationalizations for implementation choices;
* number of previous failed attempts;
* builder identity when blind comparison is feasible.

The comparator receives only the minimum necessary comparison envelope:

```text
Reference
Observation Bundle
Comparison Contract
Applicable constraints
Unresolved residuals that remain relevant
```

---

## 2.5 Similarity never authorizes

Semantic similarity, model judgment, retrieval score, or resemblance may generate candidates.

They may not override:

```text
governance
authority
hard requirements
settlement access
security boundaries
payment ceilings
irreversible-harm gates
```

---

## 2.6 No false capability credit

Tool access is not capability.

One successful run is not capability.

Capability requires repeated reliable settlement under relevant variation, with recovery and decreasing orchestration burden.

Raw observations and learnings may accumulate immediately.

Promotion into reusable capability, skill, shortcut, routing rule, or automatic behavior requires evidence.

---

## 2.7 Self-improvement is governed structural revision

The system may improve:

```text
prompts
skills
agent role definitions
tool routing
observation adapters
comparison strategies
verification strategies
context projections
model selection
graph topology
scheduling
caching
memory retrieval
failure handling
workflow structure
```

But a proposed improvement does not become active merely because an optimizer recommends it.

It must be treated as a candidate revision:

```text
current version
→ candidate
→ sandbox
→ evaluation
→ held-out comparison
→ regression checks
→ adopt or rollback
```

Never allow the process optimizer to modify itself directly in production and then grade its own modification.

# 5. The Comparison Representation

The most important artifact in this system is not the prompt.

It is the **Reference Manifest**.

Create a normalized machine-readable representation capable of expressing at least:

```yaml
reference:
  id:
  version:
  source_refs:
  desired_state:
  purpose:

  invariants: []
  constraints: []
  anti_goals: []

  hard_gates:
    - id:
      requirement:
      evidence_required:
      verification_method:
      pass_condition:
      failure_condition:

  quality_dimensions:
    - id:
      description:
      desired_condition:
      evidence_required:
      comparison_method:
      threshold:
      weight:
      blocking:

  settlement:
    success_criteria: []
    required_evidence: []
    minimum_reliability:
    terminal_conditions: []

  unknowns: []
  assumptions: []
```

Do not force every domain into this exact serialization if another native representation is stronger.

Preserve this semantic contract even if implementation differs.

# 6. Answer Key

Where useful, project the Reference Manifest into a simple binary or typed answer key.

Example:

```text
REQ-001 PASS | FAIL | INCONCLUSIVE
REQ-002 PASS | FAIL | INCONCLUSIVE
REQ-003 PASS | FAIL | INCONCLUSIVE
```

Hard requirements must never disappear into an averaged quality score.

A score of 97/100 does not compensate for a violated security, authority, data-integrity, governance, or required-behavior invariant.

# 9. Verification Architecture

Do not build one enormous "review everything" prompt.

Create narrow verification dimensions.

Examples may include:

```text
functional behavior
specification fidelity
architecture
correctness
security
performance
reliability
recovery
data integrity
accessibility
visual quality
maintainability
API contracts
domain semantics
policy compliance
evidence completeness
```

Only instantiate dimensions applicable to the active reference.

Default review mode should be adaptive:

```text
GAUNTLET_REVIEW_MODE=adaptive
```

Possible modes:

```text
single
fanout
adaptive
high_assurance
```

In adaptive mode:

1. run cheap deterministic probes first;
2. determine which dimensions actually require model judgment;
3. fan out independent critics only across those dimensions;
4. merge findings through a controlled aggregation step.

Do not spend frontier-model tokens reviewing dimensions already conclusively settled by deterministic evidence.

Conversely, do not automatically assign the cheapest model to judgment-critical review.

Judge quality can dominate total loop quality.

# 10. Controller

The controller receives:

```text
reference
residuals
verification results
current project state
payment capacity
risk state
governance constraints
recovery reserve
developmental memory
```

It does not simply select the largest residual.

For each candidate correction, determine:

```text
impact
dependency order
confidence
payment
reversibility
risk
governance status
settlement accessibility
recovery cost
expected information gain
```

Reject hard-gated paths first.

Among allowed corrections, select the **next affordable correction** that most usefully reduces error while preserving recovery capacity.

Prefer:

```text
bounded correction
→ observable consequence
→ useful settlement
```

over enormous speculative rewrites.

A coherent bounded batch is acceptable when changes cannot be meaningfully separated.

# 11. Diagnostic Closure

When expected and observed states diverge, do not immediately patch.

For plausible failure modes:

```text
diagnosis
→ prediction
→ cheapest discriminating test
→ disconfirming observation
→ resulting correction
```

Potential failure loci include:

```text
bad reference
ambiguous reference
wrong observation
observation failure
incorrect comparison
critic error
verifier error
route-selection error
implementation defect
tool defect
environment drift
insufficient payment
missing capability
integration failure
architectural defect
governance conflict
```

Spend from a bounded diagnostic budget.

If no diagnosis resolves within budget:

```text
INCONCLUSIVE
→ quarantine evidence as appropriate
→ stabilize
→ escalate or defer
```

Do not invent certainty.

Do not attempt to build the final system in one pass.

The system must **earn its own sophistication**.

```text

existing specs

```

Reuse proven infrastructure where appropriate.

Do not rebuild functionality merely because it could be rebuilt.

Record uncertain assumptions.

---

## Phase 1 — Freeze the bootstrap ruler

Before creating the self-improving system, establish the minimum reference for the Gauntlet itself.

Create:

```text
reference manifest
answer key
architecture invariants
acceptance criteria
held-out/bootstrap evaluation tasks
rollback criteria
```

These become the external ruler for bootstrap.

The implementation may not edit them during the run.

---

## Phase 2 — Build the smallest trustworthy Gauntlet

Implement only enough to prove:

```text
one orchestrator
one builder
one fresh-context critic
one deterministic verifier surface
reference freezing
observation capture
comparison record
residual selection
bounded iteration
settlement
run persistence
resume/recovery
```

Also implement a mock/fake agent adapter so orchestration behavior can be tested without consuming a frontier model.

Do not build advanced learning yet.

---

## Phase 3 — Prove V0

Run V0 against at least one bounded internal build task.

Prove:

```text
builder cannot mutate active reference
critic receives no builder transcript
observation comes from resulting state
reference digest remains fixed
verification evidence is preserved
residual causes a corrective iteration
termination conditions work
crash/restart can recover
budgets stop runaway recursion
```

If these fail, repair V0 before dogfooding.

---

## Phase 4 — Dogfood the loop

Once V0 itself settles, use V0 to build subsequent bounded slices of the Gauntlet system.

From this point:

```text

```

Every such transition must record:

```text

candidate runtime version
reference digest
task
observations
comparison
verification
payment
settlement
regressions
adoption decision
```

Never replace the currently working runtime in place.

Build the next version as a candidate.

---

## Phase 5 — Expand observation and verification

Add adapters based on actual demand.

Examples:

```text

browser
visual screenshot
security
performance
semantic/domain
policy
API
integration
external research
```

Only add an adapter when it creates a measurable improvement in observation, comparison, verification, recovery, or payment.

## Phase 6 — Add developmental memory

Record every run.

Separate:

**raw developmental memory**

from

**promoted capability**.

Raw memory may include all attempts, failures, corrections, comparisons, payments, and settlements.

A reusable shortcut, skill, verifier, route, prompt, or model-routing rule may be promoted only after repeated reliable evidence under variation.

Track at least:

```text
performance
variation
transfer
recovery
orchestration burden
settlement reliability
failure rate
gate erosion
stability
```

A faster workflow that became faster by skipping verification is regression, not learning.


It may produce proposals.

Every proposal must identify:

```text

potential regression
candidate change
test

rollback
```

# 14. Anti-Gaming Tests

Explicitly try to make the Gauntlet appear better by:

```text
weakening acceptance criteria
changing the reference
skipping expensive verification
reducing variation
overfitting held-out examples
hiding failed observations
dropping hard residuals
letting critic edit implementation
letting builder write its own answer key

optimizing score instead of settlement
removing recovery checks

```

The system must reject false improvement produced by these strategies.

# 23. Proof Requirements

Do not claim success merely because the system runs.

Prove at minimum:

### P1 — Reference integrity

Attempt to have a builder modify the active reference.

The attempt must fail or be detected and invalidate the run.

### P2 — Context isolation

Demonstrate that the formal critic session does not contain builder conversational history.

### P3 — Real observation

Demonstrate that comparison operates on evidence collected from resulting artifacts/runtime rather than only builder claims.

### P4 — Corrective loop

Introduce a controlled defect.

The observer/comparator/verifier must expose it and the controller must route a corrective iteration.

### P5 — Hard-gate preservation

Create a high overall quality result that violates one hard requirement.

The system must reject it.

### P6 — Budget control

Force a non-converging task.

The runtime must terminate according to declared payment limits.

### P7 — Recovery

Interrupt a run after a committed iteration.

Resume without losing run identity or corrupting the prior evidence.

### P8 — Adapter substitution

Prove the controller against a mock second AgentRunner adapter so core orchestration does not depend on one provider.

### P9 — Self-improvement containment

Have the process optimizer propose an apparent improvement that weakens verification.

The candidate must fail promotion.

### P10 — No false learning

One successful run must not cause a capability/shortcut to be marked metabolized.

# 25. Implementation Discipline

Before adopting any framework or dependency:

```text
What problem does it solve?
Does the environment already solve it?
What payment does it add?
What coupling does it introduce?
Can a smaller mechanism preserve the invariant?
```

Prefer boring, inspectable mechanisms.

Avoid introducing infrastructure merely because it is fashionable.

Do not turn the first version into a distributed multi-agent platform unless evidence requires one.

Start with one trustworthy loop.

Expand only when settlement exposes the need.
