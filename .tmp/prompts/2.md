# AGENTS.md

This repository builds a **portable, reference-anchored Gauntlet runtime** for agentic work.

The runtime implements the governed control loop:

**Reference → Transform → Observe → Compare → Verify → Select → Correct → Settle → Remember**

Prime-Agent is the initial orchestration harness, not the architecture. Models, providers, MCP servers, CLIs, databases, browsers, and agent harnesses are replaceable adapters.

The project is:

* spec-first;
* evidence-first;
* strict-typed;
* ports-and-adapters;
* test-centered;
* provider-independent;
* recoverable;
* governed against self-modifying its own ruler.

The optimization target is not maximum autonomy.

It is:

> **the smallest trustworthy Gauntlet that can settle enough work to earn its next increase in capability.**

Long workflows belong in `.agents/skills/`, not here.

Local subsystem rules may live in nested `AGENTS.md` files. Root rules remain authoritative unless a narrower rule explicitly specializes them without violating a root invariant.

## Source of truth

Do not infer project semantics from implementation when a stronger representation exists.

For project intent, prefer in this order:

1. frozen active Reference Manifest and comparison contract;
2. canonical specifications and accepted architecture decisions;
3. explicit acceptance criteria and proof requirements;
4. this `AGENTS.md` for development behavior;
5. current `.agents/` project memory;
6. implementation and generated projections;
7. plans and agent conversation history.

Plans describe intended work. They are not requirements.

Builder summaries are not evidence.

Generated artifacts are not authoritative semantics when they derive from a stronger source.

Never silently weaken a requirement because the implementation disagrees with it.

## Agent roles

Role boundaries are architectural boundaries.

### Orchestrator

When operating as the Prime-Agent orchestrator:

**Do not write implementation code yourself.**

Own:

* environment discovery;
* architecture;
* semantic decomposition;
* planning;
* work-item boundaries;
* agent delegation;
* interface contracts;
* acceptance criteria;
* test and evaluation design;
* verification architecture;
* evidence review;
* integration;
* settlement decisions;
* structural-revision promotion decisions.

Create the semantic skeleton and interfaces required to make delegated work composable.

Delegate bounded implementation work to worker agents.

Do not delegate responsibility for determining whether the total system actually settled.

### Builder

Builders implement bounded transformations.

Builders may:

* modify implementation;
* write tests;
* run local verification;
* create evidence produced by actual tools.

Builders may not modify:

* the active frozen reference;
* comparison criteria;
* acceptance gates;
* immutable evidence;
* prior settlement records.

A builder's statement that work is finished has no settlement authority.

### Critic / Comparator

Critics are read-only.

They compare the observed representation against the active reference under an explicit comparison contract.

A formal critic must use a fresh context.

Do not provide formal critics with:

* builder conversation history;
* builder reasoning;
* implementation rationalizations;
* number of prior failed attempts;
* builder identity when blind review is practical.

A critic identifies residuals.

A critic does not fix them.

### Verifier

Verifiers establish whether specific claims have sufficient evidence.

Prefer deterministic verification whenever the distinction is deterministically measurable.

Do not spend model judgment on something a compiler, test, schema validator, benchmark, security scanner, mutation test, browser probe, or other reliable instrument can establish directly.

### Process optimizer

Process optimizers produce structural-revision proposals.

They do not directly modify the active Gauntlet.

A proposed process improvement must be evaluated as a candidate before promotion.

## The development loop

Every meaningful change follows a bounded evidence loop.

```text
reference
→ identify bounded change
→ define relevant verification
→ implement
→ observe
→ compare
→ verify
→ inspect residual
→ correct or settle
```

For deterministic behavior, establish the failing test, check, or other discriminating observation before or alongside implementation whenever practical.

Do not write a large implementation and defer all verification until the end.

For Rust, the normal inner loop should resemble:

```bash
just check
just test
```

with the `justfile` composing the appropriate underlying tools.

Prefer `cargo nextest` as the Rust test execution engine.

A task is not complete because:

* it compiles;
* tests happened to run;
* the builder says it is done;
* a critic likes it;
* the happy path works once.

Completion requires the evidence declared by the active reference.

Never:

* skip a failing test to reach green;
* weaken an assertion to make implementation pass;
* delete a hard requirement;
* update a golden/reference artifact merely because current output differs;
* hide unavailable evidence;
* treat `INCONCLUSIVE` as `PASS`.

If a test or reference is wrong, demonstrate why before changing it.

Changing the ruler and changing the implementation are separate operations.

## Testing is measurement

Tests are part of the Gauntlet's measurement system.

A passing test means only that the tested distinctions passed.

It does not prove that the suite can detect the failures that matter.

Distinguish:

```text
the test passed
```

from:

```text
the test could discriminate the relevant incorrect behavior
```

### Rust test execution

Prefer:

```text
cargo-nextest
```

for routine Rust test execution.

Use focused tests during the inner loop and broader suites at meaningful integration boundaries.

### Mutation testing

Use:

```text
cargo-mutants
```

to test whether the suite notices meaningful erroneous program changes.

Mutation testing answers a stronger question than coverage:

> If this behavior became wrong, would the tests notice?

Do not run the entire mutation suite after every edit.

Prefer:

```text
fast checks
→ focused nextest
→ relevant integration tests
→ targeted mutation testing
→ broader mutation/regression gate at important settlement boundaries
```

Investigate surviving mutants.

Do not blindly add tests. A survivor may indicate:

* weak verification;
* an equivalent mutant;
* irrelevant behavior;
* unreachable behavior;
* missing requirements;
* a measurement limitation.

Classify the reason.

### Dependency verification

Use:

```text
cargo-deny
```

for applicable:

* security advisories;
* license policy;
* banned dependencies;
* duplicate/version policy;
* source restrictions.

Dependency policy is a settlement gate when declared by the reference.

## Type discipline

Use strict static typing wherever the implementation language supports it.

### Rust

Prefer domain types over primitive/stringly typed representations.

Use:

* enums for closed states;
* newtypes for semantically distinct identifiers and quantities;
* typed errors;
* explicit result types;
* traits as stable ports;
* state machines where state validity matters.

Do not encode important states as arbitrary strings when the type system can prevent invalid combinations.

Minimize `unsafe`.

Any `unsafe` requires:

* a concrete reason;
* a documented safety invariant;
* the smallest practical scope;
* verification appropriate to the risk.

Avoid `unwrap` and `expect` in production paths unless the invariant making failure impossible is mechanically established or clearly documented.

### TypeScript

Strict mode is mandatory.

No `any`.

Use:

```text
unknown
→ validate/narrow
→ typed value
```

Do not use broad casts to silence the compiler.

### Python

Use explicit types for public interfaces and important internal domain structures.

Prefer typed structures over unstructured dictionaries for stable contracts.

### Model boundaries

LLM output is untrusted external input.

Structured output must be parsed and validated before it becomes consequential state.

A model claiming to conform to a schema is not validation.

## Reference integrity

Every run freezes its active comparison representation.

The runtime must:

1. resolve the active reference;
2. normalize it;
3. version it;
4. calculate and preserve its digest;
5. use that immutable version for the run.

The active builder cannot modify the ruler against which its own work is being judged.

A reference revision is a different operation.

Treat it as:

```text
current reference
→ proposed reference
→ evaluate consequences
→ approve/reject
→ activate future version
```

Never:

```text
fail against reference
→ loosen reference
→ declare success
```

## Settlement

A successful tool call is not settlement.

A passing build is not settlement.

A favorable critic is not settlement.

Settlement requires the consequence and evidence specified by the active reference.

Valid terminal conditions include:

```text
SETTLED
BLOCKED
BUDGET_EXHAUSTED
ESCALATED
ABORTED
INCONCLUSIVE
```

Do not collapse these into generic success/failure.

Final summaries distinguish:

* implemented and proven;
* implemented but provisional;
* configured but untested;
* proposed;
* blocked;
* unknown.

Never promote provisional work to proven capability.

## Recovery

Preserve recovery capacity throughout autonomous work.

Checkpoint at meaningful settled boundaries.

Prefer small reversible commits over enormous speculative change sets.

Never rely on conversational memory to recover critical execution state.

A run must preserve enough durable state to:

* resume;
* retry safely;
* diagnose;
* roll back;
* abort without corrupting prior evidence.

Do not erase a working state merely because a replacement appears promising.

Candidate structural revisions are built beside the currently trusted version and promoted only after evaluation.

## Project memory

`.agents/` is the project-local agent memory and coordination surface.

Use:

```text

  OPEN_QUESTIONS.md
  DEBT_OBSERVED.md
  plans/
  specs/
  skills/
  lessons/
  reports/
  evidence/
```

Create only the portions required by the project.

### `CURRENT_STATUS.md`

Keep concise current state:

* what exists;
* what is proven;
* what is provisional;
* active work;
* immediate next settlement.

### `OPEN_QUESTIONS.md`

Record unresolved decisions that materially affect implementation or verification.

They do not become semantic truth.

### `specs/`

* mutation campaign;
* release;
* migration;
* deep architecture review;

* process optimization.

### `lessons/`

Store evidence-backed reusable lessons.

Do not store speculative preferences as learned capability.

### `reports/`

Human-readable evaluation and execution reports.

### `evidence/`

Machine- or human-inspectable proof artifacts that do not belong in the primary runtime state store.

Do not duplicate authoritative records unnecessarily.

Code generation is cheap. Long-term coupling is not.

Before adding a dependency, determine:

* what problem it solves;
* whether an existing dependency or standard library already solves it;
* whether the project actually needs the capability now;
* maintenance status;
* security history and current advisories;

## Naming

Canonical names matter to both humans and agents.

Use one name per concept.

Do not create synonyms for existing domain concepts.

Before naming a new major concept:

1. search the repository;
2. inspect canonical specifications;
3. inspect existing types/interfaces;
4. reuse established vocabulary when it represents the same distinction.

Prefer names that expose semantic roles:

```text
Reference
Observation
Comparison
Residual
Verification
Correction
Settlement
Capability
```

Do not casually substitute related words when the ontology distinguishes them.

In particular:

* a possibility is not an affordance;
* an outcome is not a final goal;
* observation is not settlement;
* comparison is not verification;
* verification is not settlement;
* access is not capability;
* one successful attempt is not capability.

Rust:

* types/traits/enums: `UpperCamelCase`;
* functions/modules/variables: `snake_case`;
* booleans should read as propositions where practical;
* error variants name the actual failed condition;
* ports name semantic capabilities, not vendor implementations.

## Performance and payment

Performance includes more than wall-clock speed.

Track relevant payment dimensions:

* latency;
* token usage;
* model cost;
* tool calls;
* retries;
* human orchestration burden;
* verification burden;
* compute;
* memory;
* recovery cost.

Do not optimize one payment dimension by silently degrading correctness or verification.

Prefer cheap deterministic evidence before expensive model judgment.

Do not run frontier critics on dimensions already settled conclusively by deterministic checks.

Conversely, do not select an inadequate cheap judge for a judgment-critical comparison merely to save tokens.

Preserve configured recovery reserve and budget limits.

Unbounded recursion is a defect.
